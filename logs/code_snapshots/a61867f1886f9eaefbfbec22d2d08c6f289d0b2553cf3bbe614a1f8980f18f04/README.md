# Ізольована оптимізація станів та подій

`baseline/` — незмінна копія 51 вихідного файла з робочого дерева на момент
початку задачі. Вона включає попередні незакомічені зміни, а не версію з HEAD.
`snapshot_manifest.json` містить SHA-256 кожного файла. `optimized/` — окрема
працездатна копія пакета та runners. Основний пакет і поточний paper rerun не
змінювалися.

## Зміни

- У гарячих циклах стан читається безпосередньо з `G._node`, без повторних
  звернень через NetworkX NodeView. Посилання на mapping не кешуються між
  операціями, тому заміна графа у clone/bind не залишає застарілих посилань.
- Midpoint-клони відновлюють стани через два впорядковані dict-values views.
  Швидкий шлях використовується тільки для клону відповідного джерела зі
  статичними вузлами та однаковим порядком вставки. Звичайний `refresh_from`
  зберігає зіставлення за ідентифікатором вузла.
- Вибір сприйнятливого сусіда використовує два проходи без тимчасового списку.
  Збережені built-in `sum`, порядок сусідів, кожний RNG-виклик, порівняння
  `cum > target` і порядок скалярної арифметики. Це важливо для Python 3.12,
  де `sum` float не можна довільно замінювати циклом `+=`.
- Orchestrator вимикає лише невикористовувані діагностичні before/after
  RNG-знімки через `capture_rng_snapshots=False`. Сам RNG, його копіювання у
  проби, cached event, pending origin/rate та залишковий intensity budget
  збережені. Standalone `MicroModel` за замовчуванням залишає RNG-знімки.
- Chain runner завантажує історичний Full-рядок після TwoScale. Свіжо
  декодований рядок не потребує `deepcopy`: він ніде не змінюється. Після
  побудови Orchestrator початкові NetworkX-графи та views звільняються;
  `gc.collect()` прибирає цикли cached EdgeViews до початку симуляції.

Точна рівність стосується наукових результатів і траєкторій. Метадані версії,
code fingerprint, час виконання та timestamp нового запуску закономірно інші.
Приватні поля `_cached_rng_before/_after` у моделях **усередині Orchestrator**
тепер `None`: це навмисна діагностична відмінність, а не зміна RNG-потоку.
Повний діагностичний 4-tuple standalone `MicroModel` перевіряється окремо.

## Перевірка

Із кореня проєкту:

```bash
.venv/bin/python optimization/state_events_v1/validate.py
```

Це обмежена послідовна перевірка, а не запуск paper suite. Вона створює новий
`output/state_events_validation_<UTC>/`, записує manifest та start/end/failure
у власний і центральний `logs/experiments.jsonl`. Наявний каталог результатів
не перезаписується. До та після перевіряються хеші основних і baseline-файлів;
зміна validation/optimized-коду під час виконання також викликає помилку.

Порівняння використовує `float.hex()` без числового допуску. Перевіряються всі
події, S/I/R, node attributes, порядок infected nodes, rates, pending proposals,
залишкові budgets та RNG-стани:

- 96 micro-випадків: SI/SIR/SIS, зважені та нульові ребра, різні seeds,
  рядкові node IDs, проміжні горизонти, імпорти, ізоляція і відновлення проб;
- 39 Full/MicroEngine-випадків: cached/uncached та compact/list сусіди,
  повторні ребра, self-loops, zero weights і `bind_static_graph`;
- 39 MicroMacro-випадків: усі виходи, dense/sparse logs, різні tau,
  нульові hazards і correction modes;
- 10 незмінених residual-clock regression-тестів;
- два короткі тести швидкості, по три повтори, зі змінним порядком версій;
- чотири повних повтори на збережених входах: dense/sparse n50, n50 з
  історичним Full-горизонтом 40000, dense n250 з вимірюванням пам'яті.

Порівнюються і baseline з optimized, і optimized з уже збереженими corrected
траєкторіями. Full не симулюється повторно: береться незмінний історичний рядок.
Для runner-перевірок допускаються тільки відмінності timestamp, версії,
fingerprint та нового TwoScale runtime; усі інші поля повинні збігатися точно.

У memory-випадку `tracemalloc` вимірює живі виділення перед `run()` і peak.
Weakrefs окремо перевіряють, що всі 11 початкових графів/view вже звільнені в
optimized runner. Peak RSS також записується, але не є тотожним живим
виділенням: Python може утримувати звільнену пам'ять для повторного використання.
Час із увімкненим tracemalloc не використовується як звичайний speed benchmark.

Перевірка охоплює обмежений набір, а не всі 19 200 paper-траєкторій. CPU під
час тестів зайнятий основним rerun, тому короткі timings є орієнтиром.

## Результат перевірки 2026-10-08

[Повний summary](../../output/state_events_validation_20261008T052505348663/summary.json)
та [manifest](../../output/state_events_validation_20261008T052505348663/manifest.json).
174 синтетичні випадки, 10 regression-тестів і чотири saved-input повтори
пройшли точне порівняння. Основні та baseline source hashes залишилися
незмінними. Validation fingerprint:
`65d21c3b3af414365c7a630c5568e7d13d3d8fb30adf651baa92665ba1a68e12`.

| Вимірювання | Baseline | Optimized | Співвідношення часу |
|---|---:|---:|---:|
| Midpoint, медіана 3 повторів | 1.301 s | 0.663 s | 1.96× |
| Micro events, медіана 3 повторів | 0.652 s | 0.374 s | 1.74× |
| Saved dense n50, весь task | 1.801 s | 1.464 s | 1.23× |
| Saved sparse n50, весь task | 8.211 s | 6.199 s | 1.32× |
| Saved n50 з extended Full, весь task | 7.686 s | 5.757 s | 1.34× |

У dense n250 (10 спільнот, 250 вузлів у кожній) живі traced виділення перед
`run()` становили **114.19 MiB → 12.22 MiB** (приблизно −89.3%). У baseline
залишалися живими всі 11 input graphs/views, в optimized — жоден.
Peak traced allocations зменшилися лише **116.98 → 113.62 MiB**, а peak RSS —
**325.37 → 321.33 MiB**: будівництво початкового NetworkX-графа досі визначає
загальний пік. Не трактувати −89.3% живих виділень як таке саме зменшення
всієї RAM або максимального споживання процесу.

## Використання копії

Копія chain runner сама імпортує оптимізований пакет, читає історичні дані з
основного проєкту й використовує окрему версію та code fingerprint. Її новий
default output: `output/chain_twoscale_state_events_v1_20261008/`.

Команда для майбутнього повного запуску користувачем:

```bash
.venv/bin/python optimization/state_events_v1/optimized/extrascripts/runners/rerun_chain_twoscale.py --run --workers 10
```

Повний запуск цією задачею не розпочинався. Копія не прискорює вже запущені
процеси основного пакета. Не підміняти вихідні файли поточного rerun і не
відновлювати його старий output новим кодом. Нові fingerprints потребують
нового каталогу; runner перевіряє це автоматично. Незмінний `baseline/`
призначений для порівняння через validator, а не для окремого paper-запуску.
