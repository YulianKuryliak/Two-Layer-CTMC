# План експериментів: коли симулятори різняться і як зменшити error (parameters-only)

**Статус**: живий документ. Доповнює `docs/TODO_experiments.md`, але переформульовує
напрям корекції під жорстке обмеження **parameters-only** і закриває методологічні
діри з `reports/critical_review_pseudoscience.md`.

---

## 1. Дві цілі

1. **Коли (WHEN)** MicroMacro відрізняється від Full Micro і **наскільки** — як
   функція *параметрів мережі*, а не окремих ручних сценаріїв. Треба карта режимів
   (regime map), а не набір OFAT-точок.
2. **Як (HOW)** зменшити error, **знаючи лише параметри** мережі. Обидва рівні не
   знають точну структуру одне одного (конкретні звʼязки, позиції, ідентичності
   boundary-вузлів). Корекція може спиратися лише на статистики/параметри:
   спектральна щілина `λ2`, `spectral_radius`, середній степінь `d`, `tau_find`,
   `kappa`, розподіл степенів boundary-вузлів як статистика, `W`, розміри громад.

## 2. Жорстке обмеження (parameters-only)

- **Дозволено** для корекції: будь-яка функція від параметрів, які макро-рівень
  може знати або оцінити (спектр, степеневі статистики, `W`, розміри).
- **Заборонено** як механізм корекції: точний список ребер, ідентичності
  boundary-вузлів, точний `a*_{ij}`, точний `B_I(t)`. Ці «oracle»-величини
  використовуємо **тільки** як верхню межу (скільки взагалі можна виправити), а не
  як розгортувану модель.

## 4. Три треки

- **Track A — WHEN**: карта режимів + ізоляція предикторів.
- **Track B — HOW**: parameters-only корекції з вимірюванням «закриття gap».
- **Track C — VALIDITY**: зробити висновки захищеними (censoring, horizon,
  calibration, negative control, power).

## 5. Експерименти

### CE-06 — Regime Map (параметри → error) — Track A
**Статус**: код готовий (`run_ce06_regime_map.py`), очікує запуску.
**Що робити**: свіп по `r = β_out/β_in × d (середній степінь) × k (інтерфейс)`
при L=10, n=100, SI, sparse `random_connected`, chain-macro. Для кожної реалізації
записати предиктори (`λ2`, `spectral_radius`, `d`, `tau_find`, `boundary_count`,
`boundary_within_degree`) і **горизонто-нормалізовані** метрики
(`ΔRMST/T_end`, `rel_W1`, `Δcompletion`, bootstrap CI).
**Навіщо**: побудувати датасет «параметри → error», щоб (a) показати *де* саме
зʼявляється різниця і (b) підготувати регресію для вибору predictor-ів корекції в
Track B. Виправляє horizon-конфаунд CE-03 через нормалізовані метрики.
**Метрики**: `ΔRMST/T_end`, `rel_W1`, `Δp`, completion; всі predictor-и як covariates.
**Запуск**: `pilot` (9×30, ~5–8 хв) → потім `full` (36×60, ~45–90 хв).
**Залежності**: немає. Перший у черзі.

### CE-07 — Calibration floor: structural vs calibration error — Track C→B
**Статус**: план.
**Що робити**: на кількох комірках CE-06 порівняти три варіанти:
(1) baseline `β_macro=β`, `W=k` (як зараз, «by fiat»);
(2) **scalar-calibrated**: єдиний множник `c` на `λ_ij`, підібраний так, щоб
середній макро-hazard збігався з виміряним exact gateway-hazard rate (агрегатно);
(3) **oracle-rate** (верхня межа, exact `a*_{ij}`).
**Навіщо**: розділити частину error, яку прибирає проста калібрація (calibration
error), від незводимої за агрегатного стану (structural error). Прямо закриває
критику §3.3 («всі bias-числа — це похибка навмисно некаліброваного макро»).
Якщо `c` можна оцінити з параметрів — це вже перша parameters-only корекція.
**Метрики**: ΔRMST(1) vs ΔRMST(2) vs ΔRMST(3) на спільному горизонті; частка
закритого gap.
**Залежності**: спирається на мережі/метрики CE-06.

### CE-08 — Negative control: clique–bridge–leaf з числами — Track C
**Статус**: план (частково згадано в статті лише якісно).
**Що робити**: мінімальна confounder-free топологія (`n=100`, `k=2`,
clique–bridge–leaf) з **повними** метриками: `W1`, `KS` (+p), `ΔRMST`, `Δp`,
bootstrap CI, при однаковому completion.
**Навіщо**: показати, що ефект **зникає/малий** там, де теорія так і передбачає —
falsifiability. Закриває §3.4 (найчистіший тест зараз підпертий нульовою кількісною
доказовістю).
**Метрики**: `W1`, `KS`, `ΔRMST`, `Δp` з CI; явна заява «negative control».
**Залежності**: немає; можна паралельно з CE-06.

### CE-09 — Boundary / gateway isolation (колишній CE-02) — Track A→B
**Статус**: план.
**Що робити**: зафіксувати все, крім конфігурації boundary-вузлів; варіювати
розподіл степенів boundary-вузлів і «gateway distance» (near/random/far) при
`|E|=const`, `k=const`, один короткий ланцюг. Записати `boundary_within_degree`,
`D_min`, `D_mean`.
**Навіщо**: перевірити, чи *статистика* boundary-степенів (параметр, не точна
структура) є предиктором error → кандидат-фіча для корекції в CE-10. Це
one-factor isolation (на відміну від змішаних свіпів).
**Метрики**: `ΔRMST`, `W1(T_last)`, `E[T_find]` vs boundary-статистики.
**Залежності**: підсилює вибір фіч для CE-10.

### CE-10 — Parameters-only correction ladder (реформований CE-05) — Track B (КЛЮЧОВИЙ)
**Статус**: частковий scaffold (`experiment_05_spectral_corrections`).
**Що робити**: увімкнути кандидат-корекції, що спираються **лише на параметри**, і
виміряти, наскільки кожна рухає MM до Full Micro (і до oracle-межі з CE-01/CE-07):
- **C1 — spectral alpha**: активувати мертвий `alpha_i` у макро-hazard:
  `(I_i/N_i)^{alpha_i}`, де `alpha_i = g(λ2)` (зараз обчислюється, але не
  застосовується у `macro_engine.py`).
- **C2 — degree-weighted placement**: розміщення імпорту зважене за *статистикою*
  степенів (boundary-degree distribution), не за точними ребрами.
- **C3 — contagiousness policy `tau_find`/`kappa`** (наявні V2–V4 CE-05).
**Навіжо**: це і є відповідь на «як зменшити error, коли рівні не знають структур».
Тест правильний (див. metrics_guide §mechanism): не «error корелює з λ2», а «чи
піднімає surrogate MM угору по драбині при фіксованих інших факторах» + out-of-sample
валідація на нових мережах CE-06.
**Метрики**: залишковий `ΔRMST` після корекції; частка закритого gap відносно
oracle; чи не псує negative control (CE-08).
**Залежності**: CE-06 (фічі + out-of-sample мережі), CE-07 (oracle-межа), CE-09
(вибір boundary-фіч).

### CE-11 — Horizon-controlled re-analysis of CE-03 — Track C
**Статус**: план (переважно re-analysis, нова симуляція не обовʼязкова).
**Що робити**: переаналізувати beta-ratio на **спільному** горизонті або через
Kaplan–Meier / вирівняний completion; подавати `ΔRMST/T_end`, `rel_W1`, `Δp`.
**Навіщо**: встановити зміну знаку робастно, без horizon-конфаунду. Закриває §3.1,
§3.2 (сирі `ΔμΔ` непорівнянні через різні T_end і різне censoring).
**Метрики**: знак і величина нормалізованого зсуву vs `r`, з CI.
**Залежності**: дані CE-03 вже є; можна робити одразу.

### CE-12 — Statistical power / sample-size calibration — Track C
**Статус**: план.
**Що робити**: для ключових контрастів оцінити `N`, потрібний, щоб CI виключав нуль
(paired vs unpaired). Задокументувати правило для майбутніх запусків.
**Навіжо**: metrics_guide показав, що 100 реплік недостатньо для `k=5`
(power ≈ 25%). Уникнути «CI includes zero» як хибного null.
**Метрики**: required `N(δ, σ_Δ)`; рекомендація на сценарій.
**Залежності**: `σ_Δ` з CE-06/CE-01.

## 6. Пріоритети і порядок

1. **CE-06 (pilot → full)** — фундамент: карта режимів + датасет предикторів.
2. **CE-08** і **CE-11** — паралельно, дешеві, роблять решту захищеною
   (negative control + horizon fix).
3. **CE-07** — calibration floor (структурна vs калібрувальна помилка).
4. **CE-09** — ізоляція boundary-предикторів.
5. **CE-10** — головний deliverable: parameters-only корекція, вимір «closed gap».
6. **CE-12** — по ходу, для планування `N`.

## 7. Спільні методологічні правила (для всіх експериментів)

- **Censoring-aware**: спершу completion; при різниці >5–10% — RMST/survival, не
  cond. mean/median.
- **Paired seeds**: та сама мережа/RNG для Micro і всіх MM-варіантів (прибирає
  between-run дисперсію).
- **Horizon commensurability**: сирий `ΔRMST` лише в межах одного T_end; крос-сценарно
  — нормалізовані метрики.
- **Effect-independent normalization**: поряд з `rel_W1` подавати `W1/IQR` або
  `W1/ΔT_hop`.
- **Calibration disclosure**: маркувати uncalibrated числа; подавати structural floor.
- **Negative control**: щонайменше один кейс, де ефект має зникнути (CE-08).
- **Parameters-only**: жодна корекція не читає точну структуру; oracle — лише межа.
