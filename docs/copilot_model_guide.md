## 2. Типи задач у проекті та рекомендований tier моделі

> ⚠️ **Назви моделей нижче — орієнтовні.** Точний список залежить від твого плану Copilot і дати. Перед використанням **звір з dropdown моделей у Chat** і онови назви в `.agent.md`, якщо не збігаються. Правило вибору — за *роллю* (швидка / збалансована / сильна проза / reasoning), а не за конкретною назвою.

### Tier 1 — Дешева/швидка модель
*Роль: найдешевша доступна. Напр. GPT-*-mini, Gemini Flash, Haiku-клас.*

Використовувати для:
- пошук файлів, перевірка шляхів, `grep`-подібні задачі
- перевірка LaTeX labels, `\ref`, `\cite`, `\label` консистентності
- перегляд CSV-даних, виведення таблиць з існуючих файлів
- механічні заміни рядків (rename variable, fix typo)
- перевірка чи файл існує, чи команда зібралась
- polling / status monitoring (чи CE-03 завершилось)
- перегляд логів без аналізу

**Правило Copilot:** явно перемикай model picker на mini/flash перед цими задачами.

---

### Tier 2 — Збалансована модель (DEFAULT)
*Роль: сильна універсальна не-reasoning модель. Напр. Sonnet-клас, GPT-*-класична.*

Використовувати для:
- написання Python-скриптів для нових експериментів (run_ce*.py)
- написання укр. звітів (Markdown): ΔRMST, bootstrap CI, інтерпретація
- читання + аналіз CSV з результатів симуляцій
- debugging Python/LaTeX помилок
- дрібні правки в секціях статті (один параграф)
- компіляція pdflatex + виправлення помилок
- написання нових TeX-репортів (reports/claude_experiments/)

**Правило:** це твій DEFAULT. Не перемикай на дорожчу модель, якщо задача вирішується на цьому рівні.

---

### Tier 3 — Сильна модель для прози статті
*Роль: найсильніша модель для письма. Напр. Opus-клас, GPT-*-flagship.*

Використовувати для:
- переписування / реорганізації цілої секції статті (Introduction, Discussion)
- висновок (Conclusion) статті
- фінальне шліфування прози, узгодження термінології по всій статті
- перетворення чорнових результатів у публікаційний текст

**Правило:** Tier 3 — це **виконання письма** на найвищому рівні, коли *напрям уже зрозумілий*. Якщо ще треба **вирішити що писати** — це Tier 4 нижче.

---

### Tier 4 — Reasoning / мислення над статтею ⭐
*Роль: модель з extended thinking / найсильнішим reasoning. Напр. reasoning-режим Opus, o-серія, GPT-*-thinking.*

**Це саме той режим, який ти просив — «думання над ідеями і над тим що робити».**

Використовувати для:
- **стратегія статті**: який наратив, яку історію розповідають дані, що є головним внеском
- **інтерпретація несподіваних результатів**: напр. sign flip у CE-03 (ΔRMST додатний при r=0.1) — що це означає механістично, чи це підсилює чи ламає тезу статті
- **design нових експериментів**: чому саме такий діапазон γ, які контролі потрібні, що доведе/спростує гіпотезу (CE-05 bridge-aware)
- **перевірка математики**: consistency формул $\lambda_{ij}$, approximation bounds, чи коректний висновок з CI
- **critical review як рецензент**: де претензії не підкріплені, які експерименти бракують
- **планування наступних кроків**: що робити після CE-03/CE-04, у якому порядку, з якими ризиками
- відповіді на «чому» — механізм, а не опис

**Правило:** вмикай Tier 4, коли ціна помилки — **науковий напрям**, а не рядок коду. Для таких задач:
- дай моделі повний контекст (числа inline, гіпотезу, попередні результати)
- проси міркувати вголос / зважити альтернативи, а не одразу писати текст
- це найдорожчий режим — використовуй точково, але **не економ тут за рахунок якості ідей**

## 4. Агенти Copilot: так, кожен обирає свою модель

### Як це працює
У `.agent.md` frontmatter є поле `model:`. Copilot вибирає першу доступну модель з масиву (решта — fallback). Порядок = пріоритет. Став на перше місце найсильнішу для ролі, на останнє — гарантовано доступну:

```yaml
model:
  - "<найсильніша reasoning у твоєму picker>"   # перший вибір
  - "<сильна проза>"                       # fallback
  - "<збалансована>"                        # останній fallback
```

> ⚠️ **Конкретні назви в `.agent.md` можуть бути застарілими.** Якщо агент мовчки fallback’ить на default — відкрий model picker і онови назви. Головне — **роль/tier**, не точна назва.

Файли агентів кладуться в **`.github/agents/*.agent.md`** — вони автоматично доступні у VS Code через agent picker.

### Агенти що вже створені для цього проекту

| Файл | Назва | Роль (Tier) | Задача |
|---|---|---|---|
| `file-inspector.agent.md` | file-inspector | mini / flash (Tier 1) | LaTeX labels, CSV preview, log reading, path checks |
| `report-writer.agent.md` | report-writer | balanced (Tier 2) | Ukrainian markdown reports в `docs/` |
| `code-writer.agent.md` | code-writer | balanced (Tier 2) | Python experiment scripts, debugging |
| `paper-writer.agent.md` | paper-writer | strong prose (Tier 3) | LaTeX paper sections, TeX reports |
| `paper-reviewer.agent.md` | paper-reviewer | **reasoning (Tier 4)** | Critical review, math check, validity |

### ⭐ Рекомендований новий агент: `paper-strategist` (Tier 4, reasoning)

Зараз немає окремого агента для **мислення над ідеями та плануванням**. `paper-reviewer` критикує готове, але не генерує напрям. Варто додати `paper-strategist.agent.md` (тільки `read`/`search`, без `edit`) з найсильнішою reasoning-моделлю для:
- «який наратив статті», «що є головним внеском»;
- «що робити далі», планування експериментів;
- інтерпретація несподіваних або суперечливих результатів (sign flip CE-03).

Це той агент, де **якість роздумів важливіша за економію токенів**.

### Як викликати
У VS Code Copilot Chat:
```
@file-inspector перевір чи всі \label{} мають \ref{} в paper/text.tex
@report-writer напиши Ukrainian report для CE-03 з даних output/claude_experiments/ce03_beta_ratio/summary.csv
@paper-reviewer зроби critical review секції Results
@code-writer напиши run_ce05.py для bridge-aware hazard experiment
```

> 💡 Для **мислення над напрямком статті** (не готовий текст, а ідеї) — або створи `paper-strategist` (вище), або просто виклич `@paper-reviewer` з прямим проханням «зважуй вголос, розглянь альтернативи» — він на Tier 4.

| Codex (AGENTS.md) | Copilot (.agent.md) |
|---|---|
| `gpt-5.6-luna` → `paper_searcher` | mini/flash → `file-inspector` |
| `gpt-5.6-terra` → `data_checker` | balanced → `code-writer` / `report-writer` |
| `gpt-5.6-sol` → `paper_writer` | strong prose → `paper-writer` |

## 5. Економія токенів Copilot: практичні правила

### Перед запитом
- Прикріплюй **тільки потрібні файли** через `#file:` або `@workspace` для конкретного пошуку.
- Для статті: передавай тільки **відповідну секцію** `text.tex`, не весь файл (52 сторінки).
- Для даних: передавай summary.csv, а не raw per-run files.
- Для звітів: передавай лише метрики у тексті, не прикріплюй весь TeX-файл.

### Під час задачі
- Якщо Copilot "забуває" контекст — вклади у запит короткий bullet-list ключових фактів замість перечитування файлів.
- Не проси "переглянь весь репозиторій" — опишуй що саме треба знайти.
- Для механічних задач (LaTeX fix) — дай error message і одне місце, не більше.
### ⭐ Де **НЕ треба** економити (важливо)
Економія токенів має сенс на механічних задачах. Але **на мисленні над статтею економити не треба**:
- вибір наративу, головного внеску, структури статті;
- інтерпретація несподіваних або суперечливих результатів;
- design нових експериментів та планування наступних кроків;
- перевірка математики та коректності висновків.

Правило: **одна слабка розмова на Tier 4 часто дешевша, ніж 5 дешевих ітерацій на Tier 2**, якщо мова про наукове судження. Погана ідея, написана швидко, коштує більше, ніж година reasoning-моделі.
### Мовне правило (звіти)
- **Текст звіту** → українська: аналіз, висновки, опис механізмів
- **Терміни та метрики** → англійська: ΔRMST, bootstrap CI, rel-W₁, rate abstraction, import placement, chain-of-cliques, MicroMacro, Gillespie
- **Коди моделей, параметри, назви файлів** → завжди англійська: `beta_out`, `gamma`, `T_end`, `r=0.1`
- **Легенди та заголовки таблиць** → англійська (LaTeX) або змішана (Markdown)
- Не перекладай RMST, W₁, CI, SI, SIR — це прийняті абревіатури

## 7. Аналіз трейдофу: чому новіші моделі ⭐

Загальне правило Copilot: **новіше покоління тієї самої родини зазвичай дає кращу якість при тому самому або нижчому request-multiplier**. Тому за рівної/меншої ціни завжди бери новішу.

| Було (старе) | Стало (нове) | Чому раціонально |
|---|---|---|
| GPT-4.1 mini, gemini-2.0-flash | **Gemini 2.5 Flash, Haiku 4.5** | швидше й розумніше за ту саму (або нижчу) ціну; 2.0-flash і 4.1-mini вже застарілі |
| Claude Sonnet 4 | **Claude Sonnet 4.5** | краща якість коду/прози за тим самим multiplier |
| GPT-4o | **Gemini 2.5 Pro** | сильніший fallback для коду/аналізу, сучасне покоління |
| Claude Opus 4 + o3 (два окремі) | **Claude Opus 4.8** | одна модель покриває **і прозу, і extended-thinking reasoning** — простіший fallback, краща якість ніж o3 |

**Практичне правило оновлення:** коли в picker з'являється нова minor-версія (напр. Sonnet 4.6/4.8, Haiku 5, Opus 5) — став її на перше місце в `.agent.md`, якщо (multiplier ≤ поточного) І (якість ≥ поточної). Стару залиш як fallback.

> Примітка: агент бере першу **доступну** модель з масиву і просто пропускає ті, яких немає у твоєму плані. Тому «аспіраційні» нові назви безпечно ставити першими, доки в кінці ланцюга є гарантовано доступна (Sonnet 4.5).

## 9. Паралельні агенти: коли запускати кілька одночасно

Кілька агентів у паралель — це спосіб **або зекономити ліміт** (дешеві read-only агенти роблять чорнову роботу, дорога модель лише синтезує), **або з тим самим лімітом закінчити швидше** (N незалежних задач ідуть одночасно, а не послідовно).

### Коли варто (✅)

- Задачі **незалежні** й **обмежені** (кожна має чіткий вхід/вихід).
- Робота **read-only**: пошук, інспекція CSV, перевірка LaTeX-міток, tail логів.
- Приклад fan-out: один `file-inspector` перевіряє labels/refs у `paper/text.tex`, другий прев'ю `output/.../summary.csv`, третій шукає, де вжито концепт — усі паралельно на Tier 1.

### Коли НЕ варто (❌)

- Кілька **write-capable** агентів на **той самий файл** → конфлікти правок.
- Симуляції / регенерація графіків у паралель без явного дозволу.
- Задачі залежні (вихід одного = вхід іншого) → тільки послідовно.

### Патерн «fan-out → synthesize» (найдешевший)

1. **Fan-out** (паралельно, Tier 1, дешево): 2–4 `file-inspector` збирають факти з різних файлів/директорій.
2. **Synthesize** (один раз, Tier 3/4): `paper-writer` або `paper-reviewer` отримує зведені факти й робить один якісний прохід.

Ефект: дорога модель бачить лише стислі факти замість сирих файлів → менше токенів на дорогому multiplier при тій самій (або кращій) якості.

### Guardrails

- Тримай concurrency **обмеженим (2–4)** — більше рідко дає виграш і з'їдає ліміт.
- Дублюй політику `AGENTS.md`: read-only паралелиться вільно; write-capable — ніколи на спільний файл/директорію.
- Якщо не впевнений, що паралелізм окупиться — не паралель.
